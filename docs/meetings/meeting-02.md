## 三、议题与结论

### 议题 1：后端目录结构

**结论**：后端统一为 `backend/app/`（main / routers / schemas / services / repositories / models）+ `backend/tests`，不再保留仓库根目录下的旧扁平副本。

**责任人**：全组

**说明**：延续第一次会议 ADR-002 的分层约定；后续新增后端代码一律放入 `app/` 对应分层，根目录遗留的旧 `api/ core/ models/ schemas/ tests/` 文件随合并逐步清理。

### 议题 2：小程序目录

**结论**：前端统一收敛到 `frontend/`，页面放在 `frontend/pages/<模块>/`；早期试点的 `miniprogram/` 目录不再使用。

**责任人**：B · 宋沛蕾（@kindly-cs）

### 议题 3：中期检查材料

**结论**：需入库的中期材料包括——架构文档（#28）、分支保护截图与规则说明、CI 配置、Alpha Release `v0.1.0-alpha`、不少于两份会议记录。

**责任人**：A · 何佳欣（@H1230666）牵头，全组配合核对。

### 议题 4：开发与合并流程

**结论**：禁止直推 `main`；统一流程为 `feature/<issue号>-<简述>` 分支 → 提交 PR → 1 名非作者 Approve → 合并。

**责任人**：全组

### 议题 5：评审要求

**结论**：每个 PR 至少 1 条行内评审，须写清“问题 + 原因 + 建议”；评审意见 48 小时内响应；固定由 A 评审 D 的 PR，禁止自评自合。

**责任人**：全组

### 议题 6：PR 数量与分支清理

**结论**：一个 Issue 对应一个 PR；PR 合并后删除对应特性分支，避免分支堆积。

**责任人**：全组

## 五、决议摘要（用于答辩复述）

1. 后端按 `backend/app` 分层、前端收敛到 `frontend/`，清理历史目录副本。
2. 所有变更走 PR：特性分支 → 1 人 Approve → CI 通过 → 合并，禁止直推 main。
3. 评审必须落到行内，写明问题、原因与建议，48 小时内响应。
4. 中期材料以架构文档、分支保护说明、CI、Alpha Release、两份会议记录为准。
5. 一个 Issue 一个 PR，合并即删分支，保持仓库整洁。
